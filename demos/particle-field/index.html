Particle Field

Tens of thousands of particles advected through a flow field and deflected by the pointer. Plain 2D canvas, no library — the whole thing is one typed array and one putImageData.

—

How it works

Every particle stores four floats — x, y, vx, vy — in one flat Float32Array. Per frame it samples a curl-free value-noise field for an angle, accelerates along it, and integrates. That is the entire simulation. 

for (let i = 0; i < n; i++) {
  const o = i * 4;
  const a = noise(p[o] * s, p[o+1] * s, t) * TAU * 2;
  p[o+2] += Math.cos(a) * force;   // vx
  p[o+3] += Math.sin(a) * force;   // vy
  p[o+2] *= drag; p[o+3] *= drag;
  p[o]   += p[o+2];
  p[o+1] += p[o+3];
}

Why it stays fast

  • One typed array, no objects. 40 000 particle objects means 40 000 allocations the GC has to walk; one Float32Array is a single contiguous block and stays in cache.
  • Writing pixels, not drawing shapes. fillRect per particle costs a state change each time. At this count it is far cheaper to write bytes into an ImageData buffer directly and blit once.
  • Trails without stored history. The previous frame is faded by compositing a translucent black rectangle over it, so each particle's tail is free.
  • Value noise, not Perlin. A hashed lattice with smooth interpolation is a few operations and visually indistinguishable at this scale.

Where the ceiling is

On this path the main thread does everything, so ~150k particles at 60fps is roughly the limit on a laptop. Past that, move the integration to a GPU compute pass — see the GPU Compute Particles demo, which runs a quarter of a million with the CPU idle.
